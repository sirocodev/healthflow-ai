# 자체 취약점 점검 결과 (공유 전 리뷰)

이 문서는 코드 공유 전에 직접 점검하고 반영한 항목들입니다.

## v2 업데이트 — 로그인 제거 후 재점검 (익명 세션 구조)

로그인/회원가입을 없애기로 하면서 "누가 이 데이터의 주인인가"를 증명할 방법이 사라졌습니다.
이건 익명 서비스에서 가장 흔한 취약점 지점이라 별도로 다시 점검했습니다.

- **문제**: session_id를 클라이언트가 body/query로 보내는 방식이면, UUID를 추측하거나
  유출된 값 하나로 다른 사람의 생리주기·수면 데이터에 접근할 수 있음 (로그인 있을 때보다 오히려 위험도가 높아짐).
- **수정**: `lib/session.ts`에서 서버가 session_id에 HMAC 서명을 붙여 HttpOnly+Secure 쿠키로만
  내려주고, 모든 API는 이 쿠키를 검증해서만 session_id를 얻음. 클라이언트가 보낸 session_id는 절대 신뢰하지 않음.
- **DB 레벨 방어**: 익명 구조에서는 `auth.uid()` 기반 RLS를 못 쓰므로, 모든 테이블에 RLS는 켜두되
  정책을 아예 만들지 않아 anon key로는 완전히 차단. 실제 조회는 Next.js 서버에서 service role
  키로만 수행하고, 그 서버 코드 안에서 세션 쿠키로 검증된 session_id로만 범위를 제한.
- **데이터 분리**: `feedback_contacts`(이메일)는 건강 데이터 테이블과 FK로 전혀 연결하지 않음 —
  이메일 유출이 곧 건강 데이터 유출로 이어지지 않도록.
- **보존 기간**: `anonymous_sessions.expires_at` + `purge_expired_sessions()` 함수로 사용자가 고른
  보존기간(1/7/30일)이 지나면 자동 삭제되도록 설계 (pg_cron으로 매일 실행 권장).

## v1 발견 → 수정한 항목 (로그인 있던 버전 — 현재는 위 v2로 대체)

1. **IDOR (다른 사용자 데이터 접근 가능성)**
   - 문제: API에서 요청 바디의 `user_id`를 그대로 신뢰하면, 다른 사용자의 건강/생리 데이터를 조회할 수 있음.
   - 수정: `/api/ai-recommendation`은 Supabase 세션에서 얻은 `user.id`만 사용하고, 모든 테이블에 RLS(`auth.uid() = user_id`) 정책을 걸어 DB 레벨에서 이중으로 차단.

2. **민감 데이터 과다 노출 (프롬프트 인젝션 표면 축소 포함)**
   - 문제: LLM 프롬프트에 `memo` 같은 자유 텍스트나 생년월일 원본을 그대로 넘기면, 불필요한 민감 정보가 외부 API 로그에 남을 수 있음.
   - 수정: 프롬프트에는 점수(숫자)·카테고리 같은 요약값만 전달. 원본 텍스트는 넘기지 않음.

3. **레이트리밋 부재로 인한 비용/남용 위험**
   - 문제: LLM 호출 라우트에 제한이 없으면 스크립트로 반복 호출 시 API 비용이 무한히 증가.
   - 수정: 사용자당 분당 5회로 제한하는 기본 레이트리밋 추가 (프로덕션에서는 Redis 기반으로 교체 권장).

4. **AI 추천을 캘린더에 즉시 반영하는 구조의 위험**
   - 문제: AI가 실수로 회의를 지우거나 잘못 이동시키면 되돌리기 어려움.
   - 수정: 기획안의 "Human-in-the-loop" 원칙을 그대로 코드에 반영 — `ai_recommendations` 테이블에 `applied` 플래그를 두고, 실제 캘린더 반영은 사용자가 승인한 뒤 별도 라우트(`/api/calendar/apply`, 추후 구현)에서만 수행하도록 분리.

5. **생리주기 계산의 오기입 데이터 오염**
   - 문제: 사용자가 실수로 시작일을 두 번 입력하거나 간격이 비정상적인 경우, 평균 주기 계산이 크게 틀어질 수 있음.
   - 수정: 15~45일 범위를 벗어나는 간격은 이상치로 간주해 평균 계산에서 제외.

6. **LLM 호출 실패 시 서비스 전체가 멈추는 문제**
   - 문제: OpenAI/Anthropic API 장애 시 사용자가 아무 것도 못 보게 됨.
   - 수정: LLM 호출을 try/catch로 감싸고, 실패 시에도 이미 계산된 점수는 반환 + 안전한 fallback 문구 제공.

## 아직 반영되지 않아, 실제 구현 단계에서 반드시 챙겨야 할 것

- **Google OAuth 토큰 저장**: `calendar_connections.encrypted_refresh_token`은 pgcrypto의 `pgp_sym_encrypt()` 등으로 반드시 암호화. 절대 평문 저장하지 않기.
- **medical disclaimer**: 기획안 13번에서 언급한 대로 "의료 진단 서비스 아님"을 온보딩과 인사이트 문구에 명시.
- **CORS / API Route 접근 제어**: Next.js API Route가 외부 도메인에서 직접 호출되지 않도록 same-origin 체크 유지.
- **Notion 위젯 iframe 보안**: 위젯을 실제 배포하면 Notion embed는 공개 URL이 필요함 → 인증 없는 공개 페이지가 되므로, 개인화된 실데이터를 붙일 경우 만료되는 서명된 토큰(예: `?token=`)으로 접근 제어 필요. 지금 초안은 목데이터라 문제 없음.
- **SESSION_SIGNING_SECRET 관리**: `.env`에만 두고 절대 커밋하지 않기. 이 값이 유출되면 세션 서명 위조가 가능해지므로 다른 시크릿과 동급으로 취급.
- **pg_cron 스케줄 등록**: `purge_expired_sessions()`를 실제로 매일 실행하도록 Supabase 대시보드에서 cron job 등록 필요 (함수만 만들어두면 자동 실행되지 않음).
